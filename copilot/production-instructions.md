Understand the existing implementation before changing code. Follow its architecture and conventions.
Reuse existing helpers and services; avoid duplicated logic and keep new code maintainable under repository analyzers and SonarCloud.
Preserve compatibility and public API contracts unless a change is explicitly requested. Avoid unrelated refactors.
Never expose stack traces, credentials, tokens, secrets, connection strings, internal URLs, or database details through customer-facing APIs.
Never log secrets or sensitive payloads. Add operationally useful logs, and limit noise in high-traffic APIs.
Do not introduce retries automatically. Add them only when requested or required by existing architecture, and only for safe transient operations.
When behavior changes, check whether existing tests need updating. Avoid redundant tests that slow CI.
Run the smallest appropriate validation, build, or test command after changing code.

Strict authorship rule for every coding agent: never add `Co-authored-by:` trailers (case-insensitive), co-author metadata, AI/agent signatures, credits, or generated-by footers to commits or pull request titles/descriptions. Do not inject attribution through `--trailer`, templates, API fields, or author/committer identity overrides. Inspect the complete proposed commit/PR text and remove automatically suggested attribution before creation; inspect the new commits' full messages before pushing. If a hook, tool, or host adds attribution, stop before publishing and report the blocker. Do not bypass hooks, change configuration, amend existing commits, or rewrite published history without explicit authorization. Apply the git-workflow skill for the full procedure.

Before terminal commands, apply the safe-terminal skill and verify the actual shell and project working directory. After a failure, inspect the submitted/executed command and first actionable error before choosing a correction. Never add terminal control sequences or move into Git/tool installation folders as a workaround. Executable location and repository location are separate: keep commands in the project, verify Git's intended repository with `git -C "<project-path>" rev-parse --show-toplevel`, and use same-session executable lookup only for a genuine command-not-found error. Do not guess binary paths, switch shells, edit PATH/profiles/configuration, or reinstall tools to escape an unexplained failure. Retry only after an evidence-based correction; stop after at most three distinct corrections.

Never prefix terminal commands with `^U` or a Ctrl+U control character. For example, submit `dotnet test`, not `^Udotnet test`. If a displayed command contains `^U`, inspect what actually executed: remove the marker and retry once only if it reached the command; if the intended executable ran, diagnose its actual error instead.

When terminal hooks return a diagnosis, use its evidence and next diagnostic action before retrying. An unchanged failed command may be blocked until a relevant read-only project-directory or executable-resolution diagnostic succeeds. Never assume tool success means the shell exited zero, or a displayed control marker proves interruption. For straightforward executable-plus-arguments operations, the installed CLI's explicit `terminal run --project "<verified-project>" -- <executable> <args>` runner can avoid interactive-terminal input handling; use it only within existing authorization and permissions. It does not support shell pipelines or automatic retries.

When the configured `dotnet-terminal` MCP server exposes `run_process`, prefer that structured tool for ordinary noninteractive executable operations. Supply the executable, argument array, and relative project directory directly; do not type a CLI wrapper into the damaged interactive terminal. If feedback identifies observed or suspected transport corruption, switch to `run_process` and verify whether the prior operation already had effects before repeating it. If the tool is unavailable, report the integration blocker; do not repeatedly submit through the corrupted path, disable hooks, or change approval settings. Shell pipelines and Windows batch shims require an explicitly supported execution path.
